# WORKFLOW — 项目长期协作规范

> 文档类型：**长期协作规范（COLLABORATION WORKFLOW）**。
> 只记录长期稳定的协作规则，**不**记录当前阶段状态、技术架构或具体阶段计划。
> 项目当前状态、文档职责登记与权威文档入口见 `docs/PROJECT_STATE.md`；当前架构见 `docs/ARCHITECTURE.md`。
> 本文件规定「如何协作」，**不覆盖**具体任务授权、冻结契约或实际验收结果。
> Gemini 或 Codex 对话中的理解与说明不取代仓库正式文档；两者冲突时以仓库文档为准。

---

## 1. 协作角色与职责

| 角色 | 职责 |
| :--- | :--- |
| **用户** | 决定项目方向、功能优先级与阶段推进顺序；批准阶段计划、适用契约与实施范围；保留最终验收权，并决定审核发现应触发修复、有条件接受还是拒绝；授权具体 Git 操作。 |
| **Gemini** | 制定阶段计划与架构提案；起草供用户审批的阶段契约；准备交给 Codex 的实施任务指令；在 Codex 实施后独立审核代码、测试、文档、范围合规性与 Git 证据，并区分已验证事实、推断、未验证事项、风险和遗留问题。 |
| **Codex** | 只执行明确获准的任务与契约；运行适当测试和检查；更新获准修改的文档与实施记录；汇报实际变更、已执行检查、结果、遗留问题及相关 Git 证据；遇到阻断条件时停止受影响工作并报告。 |

- 三者职责不得混为一谈：**用户负责决策、批准与最终验收，Gemini 负责规划与独立技术审核，Codex 负责已批准任务的实施**。
- 规划或起草契约**不构成**实施授权。实施只有在用户批准适用范围与契约后才能开始。
- Gemini 的独立技术审核**不代替**用户的最终验收；Gemini 不得代替用户授权实施或宣布最终验收。
- Codex 可以主动做技术自检与风险分析，但**不得**替代 Gemini 的阶段规划与独立审核，也**不得**推定用户已授权任何 Git 状态变更。
- 任何一方都**不得**在未获授权的情况下静默改变项目方向、冻结决策或实施范围。
- Codex **不得**擅自决定扩大项目范围，也**不得**更改已冻结的设计。
- 遇到契约冲突、重大风险、未经授权的范围扩张、未解决的测试失败或数据安全问题，Codex 必须停止受影响的工作并报告，不得静默改变范围或架构。

## 2. 标准协作流程

1. 明确任务目标与当前基线（依据 `PROJECT_STATE.md`、相关冻结契约与实际代码）。
2. Gemini 制定阶段或子阶段计划，明确目标、范围、依赖、风险与验收标准；需要正式契约时起草契约供用户审批。
3. 用户批准适用范围与契约，并明确实施授权；未获批准的建议或草案不构成实施任务。
4. Gemini 根据已批准范围准备实施任务指令，交 Codex 执行。
5. Codex 在授权范围内完整实施，**不需要**每完成一个小步骤就暂停等待审核。
6. Codex 更新获准修改的实施记录，汇报实际变更、测试结果、未解决问题和 Git 状态。
7. Gemini 对照授权范围、冻结契约、实际差异、测试结果与验收标准做独立集中审核，并分别报告已验证事实、推断、未验证事项、风险和遗留问题。
8. 用户决定审核发现应触发修复、有条件接受还是拒绝。需要修复时，Gemini 准备新的受限任务或修订要求，Codex 据此修复并复验。
9. 由用户作出最终验收决定；满足验收标准后，按本次明确授权完成 Git 收尾。
10. 阶段正式关闭后，以已关闭的基线为起点讨论后续工作。

不是每项小任务都需要完整走一遍阶段流程，应根据任务规模合理简化；**不为了形式增加不必要的审批、报告或重复检查**，但**不能省略必要的授权、安全检查和验证**。

### 2.1 交给 Codex 的任务指令应包含

任务指令通常由 Gemini 根据用户已批准的阶段计划、契约与范围准备。包含以下内容的
草案本身仍不构成实施授权。

1. 任务目标与实施依据。
2. 允许修改的范围及禁止修改的内容。
3. 必须遵守的契约、架构与兼容性约束。
4. 必要的测试、检查及验收标准。
5. 需要暂停并报告的异常情况。
6. Git 操作授权范围。
7. 实施完成后需要提供的结果与证据。
8. 需要更新的文档，以及是否需要同步 `PROJECT_STATE.md`。

任务不涉及的项目不必机械地逐项展开，但不得留下可能导致越权实施的关键歧义。

## 3. 实施过程中的暂停条件

仅在以下情况**无法在既定范围内安全解决**时暂停并报告：

- 现有冻结契约之间存在实质冲突。
- 需要修改架构、数据模型或已冻结决策。
- 任务需要超出授权范围。
- 测试失败无法在当前范围内解决。
- 存在数据安全、数据丢失或不可逆操作风险。
- 缺少继续执行所必需的信息或权限。

报告应说明：冲突或风险、已完成的检查、可行选项，以及需要用户决定的事项。

其他正常实施步骤由 Codex **自主连续完成**，不应反复询问用户是否继续。

## 4. 新对话启动规则

开始新的规划或实施任务时，承担该任务的 Gemini 或 Codex 应先阅读：

1. `docs/WORKFLOW.md`：理解长期协作规则。
2. `docs/PROJECT_STATE.md`：了解当前基线、阶段状态、文档职责登记和权威文档入口。
3. 本次任务对应的冻结契约、实施日志、设计文档及相关代码。
4. 如存在，对应的大阶段总工作文档与小阶段工作文档。

阅读后先确认当前基线、任务依据、授权范围和验收要求。

**判断依据以仓库中的实际代码、测试结果和正式文档为准，而不是历史对话记忆**；如果仓库当前状态与旧对话内容不一致，应先核实当前事实并明确指出差异，不得把历史讨论、未经验证的建议或未冻结路线图当成当前事实或已批准任务。

如果当前任务授权不明确，应先澄清；如果授权明确，不必重复询问。

涉及具体代码实现时应检查相关代码与测试；涉及 Git 收尾或阶段状态时应核对实际 HEAD、相关 commit / tag 及工作区状态。不要求每次开始任务都重新审计整个仓库，核验范围应与任务风险和验收要求相匹配。

## 5. 文档职责摘要与维护原则

**职责登记入口**：完整的文档职责表以 `docs/PROJECT_STATE.md` §2.1 为**唯一登记入口**；文档权威顺序见该文件 §2.2。本节只保留协作时最常用的职责摘要，**不维护第二份完整表格**。

| 文档 | 协作相关职责（摘要） |
| :--- | :--- |
| `WORKFLOW.md` | 长期协作规则：角色职责、标准流程、暂停条件、文档分层与权限边界、审核与阶段状态、Git 授权规则。 |
| `PROJECT_STATE.md` | 全项目当前状态登记：基线、阶段状态、文档职责登记、权威文档入口与已知问题。 |
| 阶段冻结契约 | 阶段范围、架构约束与验收标准；**不得被工作文档替代或扩大**。 |
| 实施日志 | 记录实施依据、过程、实际结果与待处理事项。 |
| Closure Report | 阶段最终验收结论与关闭证据（含 Git 证据）。 |
| 大阶段总工作文档 / 小阶段工作文档 | 分层组织规划与上下文，**不构成实施授权**。 |
| `README.md` / `ARCHITECTURE.md` | 项目介绍与文档导航 / 当前架构与技术事实；状态摘要以 `PROJECT_STATE.md` 为准。 |

- 只在信息确实属于对应文档职责时更新文档。
- **优先更新已有的适当文档**，避免为每个小步骤创建新报告、重复记录同一信息或进行无必要的历史文档重写。
- 不得为了让文档看起来一致而**静默改写**冻结决策、历史结论或事实记录；发现矛盾时应指出冲突，并按 `docs/PROJECT_STATE.md` §2.2 的权威顺序处理。

### 5.1 大阶段与小阶段的分层

- 包含多个小阶段或工作单元的大阶段，可采用「**大阶段总工作文档 + 各小阶段工作文档**」的分层方式管理信息：总工作文档负责汇总（总体目标、简要计划、进度、成果摘要、遗留问题与索引），小阶段工作文档负责详细说明（目标与范围、实施边界、测试与验收标准、实际结果）。
- 是否需要为某项工作单独建立文档，按复杂度、持续时间、上下文独立性和验收要求决定；**不要求**为每个微小任务创建文档。
- 小阶段完成后，应将其实际状态、成果摘要与遗留问题同步到承担汇总职责的文档；涉及全项目状态变化时同步到 `docs/PROJECT_STATE.md`。
- **哪些工作文档已建立、哪些暂不建立，属当前项目决策**，一律以 `docs/PROJECT_STATE.md` 为准，不在本文件登记。

### 5.2 工作文档的权限边界

- 工作文档（总工作文档 / 小阶段工作文档 / 实施日志）用于组织规划、承接上下文、记录过程与汇总结果，**不构成实施授权**，也不能替代冻结契约。
- 工作文档不得通过新增要求、修改目标或改变验收口径，绕过既有契约与用户授权。
- 工作文档中的计划应区分建议、已批准事项和已完成事项；**不得**把尚未实施的计划写成已完成成果，也**不得**把未验证结果写成已通过验收。
- 工作文档与冻结契约、用户明确批准的范围或正式验收证据冲突时，应先暂停受影响的工作，核实冲突并报告，**不得**自行选择对实施更方便的规则。
- 如确需调整冻结契约、阶段目标、实施范围或验收标准，应先说明原因、影响与风险，取得必要授权，并按项目约定完成正式变更记录。

## 6. 验收与审核原则

- 验收标准应尽量在实施前明确。
- 根据任务风险和影响范围选择适当的测试与检查。
- 汇报必须区分：**已验证事实、推断、未验证事项、未解决问题**。
- **不得**声称执行过实际未运行的测试或检查；**不得伪造**批准记录、测试结果、提交记录、tag 或验收证据。
- **不得**仅凭测试通过就宣称所有需求均已满足。

Gemini 的独立集中审核应对照：

- 是否完成用户批准的目标，是否超出任务范围或违反禁止事项；
- 是否遵守冻结契约与现有架构约束；
- 测试与检查是否真实执行、结果是否充分；
- 是否存在数据安全、数据丢失、兼容性或状态一致性风险；
- 文档是否准确反映实际代码、已批准计划与项目状态；大阶段与小阶段工作文档是否同步；
- Git 提交、tag 与工作区状态是否符合授权与收尾要求。

### 6.1 审核结论

- **通过**：满足当前任务或阶段的全部验收标准。
- **有条件通过**：核心要求已满足，但仍有明确、可接受且已记录的非阻断事项。
- **不通过**：存在未满足的验收要求、范围违规、关键验证缺失或重大风险。

以上是 Gemini 的技术审核意见。审核发现是否要求修复、是否接受为有条件通过或是否
拒绝，由用户决定；Gemini 的结论不代替用户最终验收。

审核应优先指出实际问题，不重复无关背景；证据不足的事项应明确标记为**未验证**，而不是推断为通过。

### 6.2 验收与 Git 操作的区别

- Gemini 的审核结论是技术审核意见，**不自动**代表用户已接受验收。
- 用户接受验收，**不自动**代表已授权任何 Git 操作。
- Git 操作完成，**不自动**代表阶段已正式关闭。
- 阶段关闭以实际验收结论、必要的 Git 证据及正式关闭记录为依据。

## 7. Git 收尾原则

阶段关闭必须具备**验收结论**和**可核验的 Git 证据**（提交、tag）；未经用户明确授权，不得执行任何 Git 状态变更操作。

- 是否允许 commit、tag、push 或其他 Git 操作，**以用户针对当前任务的明确授权为准**。
- commit、创建或移动 tag、push、重写历史、清理与任务无关的修改等操作，都必须获得
  与具体任务相匹配的明确授权，不得从规划、实施、审核或阶段关闭状态推定。
- **默认规则**：Codex 可以检查和汇报 Git 状态，但**不得**自行执行 `git add` / `git commit` / 创建或修改 tag / `git push`。
- 需要授权的 Git 操作（`git add`、`git commit`、创建或修改 tag、`git push` 等）**执行前**必须先汇报变更范围、必要检查结果及当前 Git 状态，并**等待用户明确授权**。
- 只读检查（`git status`、`git diff`、提交历史、tag 查询）在任务范围内允许，应汇报实际结果。
- 用户可在任务指令中预先授权明确的 Git 操作范围；已授权范围内无须重复询问，超出范围仍须另行确认。
- 执行前核对工作区状态、完整差异、变更范围与相关检查结果；只暂存和提交本次任务授权范围内的文件。
- **不得**擅自创建、移动或删除 tag，**不得**重写 Git 历史或强制推送，**不得**清理与当前任务无关的修改。
- 提交后核对：提交 hash、文件清单、工作区状态，以及本次操作涉及的 tag。
- 如果工作区包含无关修改、变更范围不明确、检查失败或发现潜在数据丢失风险，应先停止相关 Git 操作并如实报告，**不得**擅自清理。
- 测试通过、审核通过、用户接受验收或工作文档要求收尾，都**不自动**构成 Git 操作授权。

## 8. 阶段状态与区别

项目讨论、方案批准、契约冻结、实施完成、验收通过、Git 收尾和阶段关闭是**不同状态**，不得混为一谈：

| 状态 | 含义 |
| :--- | :--- |
| **讨论中** | 方案仍可调整，不构成实施授权。 |
| **已批准** | 用户同意方案或任务；仍应遵循约定的冻结与实施流程。 |
| **已冻结** | 实施范围与关键约束已确定；未经明确授权不得自行改变。 |
| **实施完成** | Codex 已完成约定工作，但仍需审核与验收。 |
| **验收通过** | 约定的验收标准已满足并有证据支持；用户尚未接受结论时仍需等待决策。 |
| **Git 收尾完成** | 已获授权的提交、tag 等操作已完成并经核验。 |
| **已关闭** | 阶段满足正式关闭条件：验收结论、必要的 Git 证据与关闭记录均已确认。 |

- 实施完成 ≠ 验收通过；验收通过 ≠ 已完成 Git 收尾；Git 收尾完成 ≠ 阶段已关闭。
- 冻结契约如确需修改，应先说明原因、影响范围及相关风险，取得必要授权后再调整，不得通过静默修改文档或代码绕过变更控制。
- 对已经正式关闭并冻结的阶段，应以现有关闭证据和当前项目状态为依据，不应无故重新打开、重复收尾或重新实施。
- 工作文档中的状态描述不能代替实际验收、用户授权与 Git 证据。

## 9. 规则优先级与冲突处理

- **用户对当前任务的明确授权**决定本次工作范围；但不能据此假装已经修改或重新批准冻结契约。
- **冻结契约**约束对应阶段的设计、范围和验收条件。
- **阶段 Closure Report** 记录该阶段的最终验收结论与收尾证据。
- **`PROJECT_STATE.md`** 用于导航和当前状态摘要，**不替代**原始契约与阶段收尾证据。
- **`WORKFLOW.md`** 规定协作方式，**不覆盖**具体任务授权、冻结契约或实际验收结果。
- **Gemini / Codex 对话说明**补充协作上下文，**不取代**上述仓库文档。
- **`README.md` / `ARCHITECTURE.md` 不得被当作覆盖冻结契约的依据**。

具体文档权威顺序（设计决策权威 = 冻结 Contract；阶段验收权威 = Closure Report）见 `docs/PROJECT_STATE.md` §2.2，本文件不重复定义。

如果发现来源之间存在实质冲突，**不要静默选择对自己最方便的版本**。应指出冲突、保留证据，并在必要时请求用户决定。
