## 1. 缺口清单

### U1 — 真实组织需求与标签粒度

| 项 | 内容 |
| :--- | :--- |
| 缺口 | 「用户到底想怎么分类」没有任何真实数据；决定 Tag 的分类粒度与默认标签，目前无法决定 |
| 现有证据 | 无（持久库 `resources=0`、`tags=0`、`resource_tags=0`） |
| 取证方式 | 在**真实工作库**上做只读统计：资源总数、用户打标数、每资源标签数分布、标签名称分布；样本量需先定义阈值（建议 ≥ 数十个真实资源且至少一次真实打标会话） |
| 关闭条件 | 达到约定样本量，并形成一份只读统计记录 + 用户对粒度的明确陈述 |
| 后续任务 | 采集真实工作库；产出统计记录；据此决定 Tag 粒度（**不在本文件决定**） |
| 状态 | **OPEN** |

### U2 — 入口先后：core→CLI 先，还是 core→GUI 先

| 项 | 内容 |
| :--- | :--- |
| 缺口 | 无真实使用反馈，无法判断入口优先级与验收方式 |
| 现有证据 | 仅有**实现进度**：Phase 3.1 已提供 CLI 写入口（`main.py resource …`）；Phase 3.2 明确把 Tag / Favorite 的入口留给 Phase 3.5。**这不是使用证据** |
| 取证方式 | 记录首个真实使用入口的选择与理由（用户会话记录 / 使用笔记）；无需新增功能代码 |
| 关闭条件 | 形成一份明确的入口偏好记录（谁在用、用什么入口、为什么） |
| 后续任务 | 在后续阶段启动前登记入口决定；若涉及 Phase 3 首期 In Scope 之外的用户可见能力，须走 Contract §16 变更控制 |
| 状态 | **OPEN** |

### U3 — 组织范围是否全局

| 项 | 内容 |
| :--- | :--- |
| 缺口 | 无多库真实样本；「组织（Tag / 收藏）是全局还是 per-library」无数据支撑 |
| 现有证据 | 无多库样本。范围层面：`docs/phase3/PHASE3_2_LOG.md` §16.2 已在**范围边界**上声明 Phase 3.2 的 Tag 只能是 GLOBAL（基于冻结 schema v2 + 全局 identity 的表达能力），并将 per-library 转 `[FUTURE-CANDIDATE]`（需 schema / architecture change）。该声明**不是**使用证据 |
| 取证方式 | 采集真实多库场景：`libraries` 数量、跨库同名 / 同内容资源比例、用户跨库组织意图 |
| 关闭条件 | 出现真实多库样本并形成明确结论，或经用户确认「单库即常态」从而按边界关闭 |
| 后续任务 | 采集多库样本；若结论为 per-library，须另立 schema / architecture 评审 |
| 状态 | **OPEN** |

### U4 — 何时需要持久 review 状态

| 项 | 内容 |
| :--- | :--- |
| 缺口 | 是否需要（以及何时需要）持久化 confirmed / dismissed 状态，无证据 |
| 现有证据 | 无（持久库 `resources=0`，无法产生 `needs_review` 样本） |
| 取证方式 | 在真实工作库上只读统计 `needs_review` 命中数与人工确认行为；记录用户是否重复处理同一批待确认项 |
| 关闭条件 | 出现真实「需要记住确认结果」的场景，且次数 / 规模达到约定阈值 |
| 后续任务 | 采集 review 样本；若成立，另立独立 schema 决策（候选 v3） |
| 状态 | **OPEN** |

### U5 — 移动场景真实发生率与容忍度

| 项 | 内容 |

| 关闭条件 | 出现真实移动实例并达到约定阈值，或经用户确认场景罕见从而按边界关闭 |
